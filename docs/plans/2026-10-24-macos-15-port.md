# macOS 15.8 port implementation plan

**Goal:** Run Glimmer on Apple Silicon Macs with macOS 15.8, using native
materials instead of Liquid Glass and preserving reliable streaming.

**Architecture:** Keep the existing streaming engine and shared app entry
points. Replace newer observation APIs with existing Observation patterns, use
older system controls, and isolate OS-specific display and fullscreen behavior.

**Tech stack:** Swift 6, SwiftUI, AppKit, VideoToolbox, AVFoundation, Sunshine's
existing protocol implementation.

## Linux implementation workflow

The implementing agent runs on Linux without Xcode, Swift or Apple SDKs. This is
the expected environment for preparing the port. Complete the source, test and
configuration changes that can be reviewed there, then hand them off for
compilation and runtime verification on a Mac.

Chunk 1 is a prerequisite for Mac verification, not for Linux implementation. Do
not stop the implementation because `xcodebuild`, `swift`, `sw_vers`, `xcrun`,
`plutil` or Apple frameworks are unavailable. Installing Linux Swift does not
provide AppKit, SwiftUI, Apple's SDKs or an Xcode app build environment.

| Chunk                 | Work to prepare on Linux                                                                                            | Checks reserved for a Mac                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1. Toolchain          | Record the toolchain requirements and handoff prerequisite.                                                         | Install or select full Xcode; confirm compiler and SDK.                                            |
| 2. Interface          | Replace glass APIs, preserve real controls, update material guidance, review layout and accessibility declarations. | Compile; inspect appearance, geometry, keyboard navigation and VoiceOver; capture screenshots.     |
| 3. Observation        | Replace both observation loops and write regression tests using existing patterns and injection points.             | Compile with strict concurrency and run tests; check Dock behavior across stream transitions.      |
| 4. Shortcuts          | Update foreground-launch declarations and relevant tests.                                                           | Compile, run intent tests and invoke the actions through Shortcuts.                                |
| 5. HDR                | Prepare the older display-layer fallback and corresponding test changes if needed for the build handoff.            | Compile; verify SDR first, then HDR on a suitable display with existing telemetry.                 |
| 6. System integration | Add presentation-option guards, update tests and review build settings and entitlements.                            | Verify fullscreen, cursor release, controllers, signed helper behavior and security compatibility. |
| 7. Integration        | Update deployment targets and version metadata, document pending verification, and review the combined diff.        | Build the app, run required checks and perform actual streaming and UI inspection.                 |

Start with chunks 2, 3 and 4, in that order. Then prepare chunk 6 and chunk 7's
deployment settings. Prepare the minimal chunk 5 compatibility path needed for a
Mac build, but defer HDR playback validation until SDR works. Keep chunks 3 and
4 sequential because they edit the same file.

Use source searches, diff review, whitespace checks and available portable
linters or script checks on Linux. Python's `plistlib` can inspect XML plist
files; it does not parse the Xcode project's OpenStep `project.pbxproj` format.
Do not rewrite the project through an unsuitable parser. Preserve its existing
structure and manually review file references and build-phase entries.

Write meaningful Swift regression tests even though this environment cannot run
them. Do not replace Apple frameworks with stubs or create a second
implementation merely to make a Linux check pass. Text searches and a second
review can find mistakes, but cannot establish that Swift compiles or that
runtime behavior is correct.

For every completed Linux task, report:

- The files changed and the intended behavior.
- The portable checks actually run and their results.
- Tests added or updated, explicitly marked as not run when applicable.
- Remaining compiler, concurrency, availability and runtime questions.
- The exact suites and manual scenarios to run on the Mac.

Mark each chunk **implementation prepared; Mac verification pending** until its
Mac checks pass. The user authorized preparing these changes on Linux; the
repository's build, screenshot and real-stream requirements remain acceptance
gates for the finished port. Do not claim the port builds, works, or is ready to
merge based solely on Linux review. Keep public compatibility claims provisional
until macOS 15.8 has been verified.

## Decisions and evidence

- The user explicitly authorized macOS 15.8 support, overriding the repository's
  macOS 26 minimum for this work.
- The user prefers removing Liquid Glass. Use native materials and real system
  controls; do not emulate glass.
- Stream-state observation must remain correct. HDR has lower priority, but
  macOS 15 already supports HDR and may only need an older display-layer
  control.
- This Mac has macOS 15.8.1, Swift 6.1.2 and the macOS 15.5 SDK in Command Line
  Tools. No full Xcode was found in `/Applications`; `make app` fails before
  compilation because `xcodebuild` requires Xcode.
- A direct compiler check of the app's 281 registered source files against the
  installed SDK stopped at missing `IntentModes` and `Observations` in
  `GlimmerIntents.swift`. This is an initial diagnostic, not an exhaustive
  compatibility check.
- There are 19 Liquid Glass uses across nine source files. There are two
  `Observations` uses, in `GlimmerApp.swift` and `GlimmerIntents.swift`.
- The installed SDK includes
  `AVAudioEnvironmentNode.isListenerHeadTrackingEnabled` from macOS 15 and
  `CALayer.wantsExtendedDynamicRangeContent` from macOS 14.
- Existing macOS 27 controller and screen-corner behavior already has
  availability checks. Preserve those checks.

## Execution rules for Luna

Take one numbered chunk per task. Read the named files and relevant architecture
documentation before editing. Report the changed files, checks run, and
remaining gaps after each chunk. Do not commit, push, publish, install the app,
change signing state, or read signing material without the user's corresponding
authorization.

Keep changes limited to compatibility and the requested material treatment.
Preserve stream tuning, saved preferences, pairing, the Wi-Fi helper offer,
keyboard navigation and VoiceOver. Add a source file only when it earns its
place, and register any new Swift file in the Xcode project. Follow the
repository's size, concurrency and license rules.

## Chunk 1: establish a usable local toolchain

**Size:** Small investigation, with an external installation prerequisite.

**Read:** `docs/CONTRIBUTING.md` setup and build guidance;
`docs/ARCHITECTURE.md` build pipeline; `Glimmer/StreamLib.xcconfig`.

1. Check `sw_vers`, `xcode-select -p`, `xcodebuild -version`, the selected SDK
   and installed Xcode bundles.
2. Prefer full Xcode 26.3 for development on this Mac. Apple lists it as
   supporting macOS 15.6 and later and shipping the macOS 26.2 SDK. This allows
   runtime availability checks around newer APIs. Verify its installation and
   licensing before using it.
3. If full Xcode is installed outside the selected location, use a per-command
   `DEVELOPER_DIR` instead of changing the system selection unnecessarily.
4. Record the exact local compiler and SDK. Keep hosted release and verification
   toolchains unchanged unless a demonstrated compatibility problem requires a
   separate change.
5. Report an installation prerequisite if Xcode is absent. Do not represent the
   current Command Line Tools as a full app build environment.

**Done when:** A full, compatible Xcode can run `xcodebuild`, or the exact
installation blocker is recorded. Xcode 16.4 is an alternative if the user
chooses it, but then all references to symbols absent from its SDK must be
removed or conditionally compiled; runtime availability checks alone are
insufficient.

## Chunk 2: replace Liquid Glass with native macOS 15 surfaces

**Size:** Medium; the largest visual chunk.

**Modify:**

- `Glimmer/GlimmerApp.swift`
- `Glimmer/ContentView+StreamButton.swift`
- `Glimmer/ContentView+ReadinessChip.swift`
- `Glimmer/ContentView+ConnectBanner.swift`
- `Glimmer/ContentViewSubviews.swift`
- `Glimmer/MenuBarPanel.swift`
- `Glimmer/PairSheet.swift`
- `Glimmer/SettingsPCsShortcutsPanes.swift`
- `Glimmer/SettingsShortcutRecorders.swift`
- `DESIGN.md` material and control guidance affected by this decision

1. Read `DESIGN.md`, `PRODUCT.md`, and the UI architecture sections. Capture the
   existing appearance where a runnable build is available; otherwise record
   that the before capture is unavailable.
2. Replace `.glassEffect`, `GlassEffectContainer`, and `.buttonStyle(.glass)`
   with system materials and appropriate standard button styles. Keep the shared
   accent button styles on real buttons.
3. Preserve control sizes, content sizing, focus, accessibility, error severity,
   and the hotkey recorder's recording state. Do not add a flexible frame to the
   launcher column.
4. Search the app for all remaining glass API uses. Remove comments that
   describe effects the app no longer uses.
5. Once the app builds, inspect light and dark appearances, pairing, empty and
   populated launchers, settings and the menu bar panel. Capture screenshots and
   perform the CONTRIBUTING geometry check if sizing changed.

**Done when:** No Liquid Glass API is required, native controls remain
accessible, and the visual inspection gaps are stated honestly.

## Chunk 3: backport both observation loops

**Size:** Medium; correctness matters more than line count.

**Modify:** `Glimmer/GlimmerApp.swift`, `Glimmer/GlimmerIntents.swift`, and
relevant tests in `GlimmerTests/SystemServiceSeamTests.swift` and
`GlimmerTests/MenuBarPresentationTests.swift`.

**Reuse:** `Glimmer/UpdaterController.swift`'s
`runPendingActionsWhenStreamEnds()` and `Glimmer/AppModel+Commands.swift`'s
`CommandStreamEnd` show existing `withObservationTracking` patterns.

1. Identify ownership and cancellation for each observer. Preserve `trackPCs`'s
   returned cancellable task or update its callers and tests deliberately.
2. Replace the Dock visibility observer with macOS 15-compatible change
   tracking, rearming after changes and reading committed state on the main
   actor. Observation callbacks can run before the new value is stored.
3. Replace the Shortcuts PC-list observer. Keep the bootstrap wait, initial
   update, rename detection, unchanged-list deduplication, and cancellation.
4. Cover repeated start/stop transitions, repeated PC changes, unchanged reloads
   and cancellation. Use existing injection points and Swift Testing; do not
   introduce polling or a general observation framework.
5. Run the affected suites when full Xcode is available. Manually check a stream
   started from the menu bar and a stream ending after the launcher has closed.

**Done when:** Both newer `Observations` calls are gone, updates continue after
the first change, and cancelled tracking stops producing updates.

## Chunk 4: preserve Shortcuts foreground launch behavior

**Size:** Small. Do this after chunk 3 because both touch
`GlimmerIntents.swift`.

**Modify:** `Glimmer/GlimmerIntents.swift`,
`GlimmerTests/GlimmerIntentsTests.swift` where useful.

1. Replace or guard `StreamIntent.supportedModes: IntentModes`, which is absent
   from the installed SDK.
2. Use the older AppIntent foreground-launch contract (`openAppWhenRun`) for
   macOS 15. Preserve the modern contract where needed without compiler
   deprecation warnings.
3. Keep the existing shared stream, wake and quit implementations and failure
   copy.
4. Run intent tests and manually invoke Stream from PC from Shortcuts. Verify
   that Glimmer comes forward and uses the requested PC and app.

**Done when:** Intent declarations compile for the chosen toolchain and
streaming through Shortcuts still opens Glimmer correctly.

## Chunk 5: add the older HDR display-layer path

**Size:** Medium, with manual display validation.

**Modify:** `Glimmer/Stream/VideoDecoder+HDR.swift`,
`GlimmerTests/VideoDecoderHDRTests.swift`, and `docs/ARCHITECTURE.md` HDR
guidance as needed.

1. Read the HDR architecture section and the existing layer configuration and
   first-frame diagnostic code.
2. Use `preferredDynamicRange` only where available. On macOS 15, use
   `wantsExtendedDynamicRangeContent` to express HDR intent. Update the
   diagnostic read as well as the setter.
3. Preserve pixel-buffer color tags, HDR metadata, negotiated bit depth, and
   existing stream tuning. Do not replace the renderer.
4. Update existing tests that directly assert `preferredDynamicRange` to check
   the appropriate OS path. Cover HDR on, HDR off and an 8-bit stream.
5. Check SDR playback first, then an HDR-capable display with HDR enabled and
   disabled. Compare displayed output and existing telemetry. If HDR cannot be
   validated, record that gap; do not claim it works or silently negotiate HDR
   and display it incorrectly.

**Done when:** SDR compiles and plays correctly; the fallback is tested, and HDR
is either validated or explicitly left as a known validation gap. Defer this
chunk only if a deliberate SDR-only policy is implemented consistently at
negotiation, settings and display configuration.

## Chunk 6: handle fullscreen and security compatibility

**Size:** Small to medium.

**Modify or inspect:** `Glimmer/Stream/StreamWindow+Fade.swift`,
`GlimmerTests/StreamWindowFirstFrameTests.swift`,
`Glimmer/Glimmer.entitlements`, `Glimmer/Glimmer-Debug.entitlements`,
`helper/Helper.entitlements`, `Glimmer/StreamLib.xcconfig`, and the helper
architecture/security documentation.

1. Preserve `.disableCursorLocationAssistance`. A follow-up compiler check
   confirmed it exists in the macOS 15 SDK; its header availability starts at
   macOS 10.11.2. The initial audit incorrectly classified it as a newer API.
2. Keep its fullscreen options assertion unconditional. Preserve the existing
   macOS 27 screen-corner guard and cursor-restoration behavior.
3. Audit newer Enhanced Security build options and entitlements for the chosen
   compiler and macOS 15 runtime. Retain compatible hardening and document
   protections that require a newer OS. Do not disable ordinary Hardened Runtime
   or library validation as a workaround.
4. Confirm that the root helper's routing socket and AWDL operations use APIs
   available on macOS 15. Its topology-observation entitlement addresses newer
   OS privacy rules; its presence alone does not establish a macOS 15 blocker.
5. Exercise fullscreen entry/exit, backgrounding, cursor release and controller
   input. Verify helper approval and restoration only through the normal
   authorized installation path.

**Done when:** Older systems avoid unavailable presentation options, cursor
restoration is correct, and security or helper uncertainties are documented
without changing signing material.

## Chunk 7: lower targets and verify the complete port

**Size:** Medium integration and validation. Final acceptance depends on chunks
1–6; Linux configuration work can proceed before Mac verification.

**Modify:** `Glimmer.xcodeproj/project.pbxproj`, `Glimmer/Info.plist`,
`Makefile`, and affected requirements in `README.md`, `PRODUCT.md`, `AGENTS.md`,
`docs/CONTRIBUTING.md` and `docs/ARCHITECTURE.md`.

1. Set a consistent macOS 15.8 minimum for app, login helper, tests, helper
   compiler target and `LSMinimumSystemVersion`. Inspect generated helper
   metadata for additional minimum-version declarations.
2. Compile with warnings enabled and fix additional API availability or compiler
   issues exposed by the real build. The initial source audit was not
   exhaustive. Use a per-command deployment-target override during earlier
   chunks if needed to expose compatibility errors before this final settings
   change.
3. Run focused tests for changed logic, then `make verify`. Read warnings in the
   build output. Run these checks with full Xcode; do not count direct type
   checking as a completed app build or test run.
4. Through an authorized installation, inspect pairing, discovery, streaming on
   Ethernet and Wi-Fi, sound, controllers, keyboard/mouse capture,
   windowed/fullscreen/mini-player modes, disconnection and reconnection,
   sleep/wake, login behavior and Shortcuts on macOS 15.8.
5. Document the tested OS, compiler and SDK, the material change, and remaining
   limitations. Follow fork versus maintainer rules for version and changelog
   ownership. Any macOS 26 support claim also needs a check there.

**Done when:** The app builds without warnings, required checks pass, and real
playback and UI inspection on macOS 15.8 support the compatibility claim. Mark
any unavailable checks as outstanding rather than declaring the port complete.

## Expected magnitude

This appears to be a moderate compatibility port, mostly in the interface and
app integration. The audit has not identified a need to rewrite transport,
decoding, pacing, controller forwarding or audio rendering. The main
uncertainties are additional errors from a full build, HDR appearance, signed
helper behavior and runtime differences during real streaming.

Use the Linux implementation order above. On the Mac, complete chunk 1 first,
then compile the prepared changes, resolve compiler findings, and finish the
checks in chunks 2–7. Stop at an unexpected architectural change and report the
evidence before expanding scope.
